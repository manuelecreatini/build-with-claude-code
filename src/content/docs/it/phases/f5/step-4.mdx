I test non sono opzionali per le funzionalità critiche. Ogni fase si chiude solo con tutti i controlli verdi.

| Livello | Cosa verifica | Strumento | Comando tipico | Quando |
|---|---|---|---|---|

## Regressioni

Una <Term id="regressione">regressione</Term>[^33] si scopre eseguendo *tutta* la suite, non solo i test nuovi: Claude la esegue alla fine di ogni fase, e la CI la ripete su ogni pull request. Per ogni bug corretto si aggiunge prima un test che lo riproduce.

## Code review: due strumenti complementari

- `/mattpocock-skills:code-review` <Role as="pocock" />: revisione su due assi, *standard* (regole del <Term id="repository">repository</Term> e un elenco classico di code smell) e *spec* (implementa fedelmente la <Term id="issue">issue</Term>?), con due <Term id="subagent">subagent</Term> paralleli. È quella che `/implement` richiama a fine lavoro.
- `/code-review` <Role as="bundled" />: cerca bug di correttezza nelle differenze correnti; accetta un livello di effort e `--fix` per applicare le correzioni. Il livello `ultra` avvia una review multi-agente in cloud (3 esecuzioni gratuite con Pro e Max, poi a crediti).
- `/simplify` <Role as="bundled" />: quattro agenti in parallelo cercano semplificazioni e riuso; non cerca bug.
- `/security-review` <Role as="builtin" />: analizza le modifiche del <Term id="branch">branch</Term> rispetto al branch principale del remote alla ricerca di vulnerabilità. Obbligatoria nelle fasi che toccano login, permessi, pagamenti o dati personali.

## Test manuale

Avvia l'app in locale (`npm run dev`, poi [http://localhost:3000](http://localhost:3000)) oppure apri l'URL di anteprima che Vercel genera per ogni pull request. Puoi farti aiutare:

- `/run` <Role as="bundled" /> avvia e usa l'app per mostrare la modifica funzionante; `/verify` <Role as="bundled" /> la costruisce, la esegue e osserva il risultato per confermare che la modifica faccia ciò che deve. Esegui una volta `/run-skill-generator` per insegnare a entrambi come si avvia il tuo progetto.
- Claude in Chrome: «Open http://localhost:3000, sign in as the test coach, create a training plan and report any console error».

Prova sempre: il percorso felice, tre casi limite (dato vuoto, dato non valido, rete lenta), il formato mobile, la navigazione solo da tastiera, la leggibilità dei messaggi di errore.

## Livello di test per tipo di progetto

| Tipo di progetto | Minimo obbligatorio | Consigliato |
|---|---|---|
| Sito vetrina, landing | Tipi, lint, build, E2E di base (home, form di contatto). | Lighthouse, controllo dei link. |
| Strumento interno, dashboard | Più: unit sui calcoli, integrazione sugli accessi ai dati. | E2E sui flussi principali, test con dati realistici. |
| SaaS con login e pagamenti | <Term id="tdd">TDD</Term> su <Term id="autenticazione-autorizzazione">autenticazione</Term>, permessi, pagamenti e integrità dei dati; integrazione su API e database; E2E da registrazione a pagamento ad azione chiave; `/security-review`. | `/code-review ultra` prima del lancio. |
| App mobile (Expo) | Unit sulla logica; E2E sui flussi principali con uno strumento per mobile. | Test su dispositivi reali iOS e Android. |
| App con funzioni AI | Test con il modello simulato; un set di valutazione (*eval*) per i prompt. | `/claude-api build-eval` per costruire il set di valutazione. |

**TDD sì**: regole di business, calcoli, permessi, pagamenti, trasformazioni di dati, correzione di bug. **TDD facoltativo**: layout puramente visivi, prototipi, script usa-e-getta.

[^32]: **Unit test**: verifica un pezzo piccolo isolato, è veloce. **Integration test**: verifica che più pezzi funzionino insieme (per esempio API e database). **End-to-end (E2E)**: simula un utente reale nel browser dall'inizio alla fine. Servono molti unit test, un buon numero di test di integrazione e pochi E2E sui percorsi critici.

[^33]: **Regressione**: un difetto in qualcosa che prima funzionava, introdotto da una modifica successiva.
